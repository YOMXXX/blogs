持续运行的 LLM 智能体有一个不太显眼但越来越贵的运维难题：模型在服务期要更新权重。个性化适配器、记忆模块、按租户微调的 LoRA，都会在会话存活的途中发布新版本。问题在于，KV 缓存是按旧版本权重算出来的——直接复用等于让模型混用两个版本推理；而安全的做法是把每个活跃会话的全部历史用新版本重新 prefill，代价随历史长度与会话数一起膨胀。11 月 23 日提交的 LiveLoRA 论文（arXiv 2611.31105，已被 NeurIPS 2026 AgenticOS workshop 接收）给了一个相当工程化的答案：不重放历史，精确迁移缓存。

> **💡 一句话概括：把 KV 缓存拆成「版本不变的部分」和「版本相关的部分」，发布新适配器时只重算后者，再用一次最新 token 的重评估把新旧版本缝起来，原子提交。**

## 问题的两难结构

先看清楚现状为什么难受。设一个智能体平台挂着 32 个活跃会话、每个 8K token 历史，适配器每发一版：

- **全历史重 prefill**：正确但昂贵。论文实测这个规模下一次发布要 4.5 秒，而且成本正比于历史长度乘会话数，会话越长寿越亏。 更糟的是如果更新频繁，重放会挤占解码算力，形成「更新越多、服务越抖」的循环。
- **直接复用旧缓存**：便宜但错误。论文给出的陈旧缓存对照实验显示，top-1 分歧率 8% 到 17%，压力场景下高达 35%，KL 散度也显著抬升——这不是可以容忍的近似，是真正的语义漂移。
- **边界重放（retained-boundary replay）**：折中方案，只在检查点保留可重放的边界状态。能对齐精度，但每会话要多存 32.41 MiB（8K 前缀），且发布延迟仍是全量方案的量级。

LiveLoRA 的目标就是把这四个变量——正确性、发布延迟、存储、解码开销——同时压下来。

## 核心机制：三个不变量换一个等价保证

方法的关键是识别出哪些东西在适配器换版时根本不变，论文用了三个设计约束：

**第一，冻结边界。** 适配器只放在最后一个解码块里，嵌入层、前面所有块、所有归一化层和 LM head 全部冻结。由于历史 token、注意力掩码、位置信息都是固定的，前 L-1 块的计算完全确定，因此最后一个块的输入 `u_t = N_L(h_{L-1,t})` 在任何适配器版本下都相同。这是整个迁移正确性的地基：历史 token 对新版本而言，只是「输入还没被消耗完的中间状态」。

**第二，版本不变的低秩坐标。** 最后一块 K/V 侧的 LoRA 采用 LoRA-FA 风格：下投影 `A_K`、`A_V` 固定，只有上投影 `B_K`、`B_V` 按版本更新。这样每个 token 的低秩坐标 `z_K,t = A_K · u_t` 跨版本不变，可以存下来当「缓存中的缓存」。

**第三，闭式重建。** 发布新版本 `v'` 时，不需要重跑任何历史前向计算，直接用矩阵乘法闭式重建全部历史位置的 K/V：

```text
k_t^(v') = R_t( k̂_t + s_K · B_K^(v') · z_K,t )
v_t^(v') = v̄_t + s_V · B_V^(v') · z_V,t
```

其中 `k̂_t`、`v̄_t` 是不可变的基础投影，`R_t` 是 RoPE 的位置相关线性映射。重建从不可变基础状态出发而不是累积参数增量，避免误差累积。单会话 n 个 token 的重建成本是 `Θ(n · r_K · d_K + n · r_V · d_V)`，低秩 r 很小，远低于重跑整个前向。

最后一步是**最新 token 重评估加原子提交**：K/V 迁移完成后，运行时在最新位置用候选版本的 Q/O/MLP 适配器重新评估该 token，得到候选 next-token logits；然后把适配器、KV 缓存、logits 作为同一个一致版本原子交换。如果准备期间前缀变了就拒绝更新。论文证明了续写等价定理：在精确算术与上述模型假设下，迁移后的 next-token 分布与全历史重 prefill 完全相同，对任意固定未来续写也保持条件分布相等。

## 数字盘点：加速在哪、代价在哪

实验平台是 Qwen2.5-3B-Instruct、单张 H200、BF16：

| 场景 | LiveLoRA | 全历史重 prefill | 中位加速 |
|------|----------|------------------|----------|
| 单会话 2K | 17.15 ms | 40.78 ms | 2.38× |
| 单会话 8K | 17.17 ms | 150.05 ms | 8.79× |
| 单会话 32K | 17.59 ms | 919.21 ms | 51.06× |
| 32 会话 × 8K | 65.71 ms | 4534.46 ms | **68.98×** |

规律很清晰：LiveLoRA 的发布延迟几乎不随历史增长（单会话 2K 到 32K 只从 17.15 涨到 17.59 ms，因为主要成本是重建加一次注意力扫描），而重 prefill 是线性爬坡。规模越大、会话越多，差距越大。

代价方面：解码时多了低秩坐标重建，相对原生缓存解码约 4.8% 开销（2K 到 32K 稳定在 4.75% 到 4.88%）；存储上紧凑保留比边界重放省 3.42 倍（8K 前缀 9.48 MiB 对 32.41 MiB），32 会话场景总内存只多 3.31%。数值正确性上，迁移后的 K/V 对参考重 prefill 最大绝对误差为零，BF16 下贪心解码选择全部一致。

## 我的工程判断：能不能用，坑在哪

**结论先行：方向正确、数学干净，但现在用不了，而且它的适用前提比加速数字更值得细看。**

第一，**没有代码**。论文全文没有 GitHub 链接，作者来自 Ryquo 与 App-In Club（后者是学生组织背景），没有伴随开源。里面所有运行时协议——适配器副本持锁复制、候选张量锁外准备、提交时原子交换——都要自己实现，这部分工作量不小于算法本身。

第二，**训练配方被绑死了**。适配器只能放最后一块、K/V 下投影不可训练、嵌入与归一化冻结——这不是实现选择，是等价定理的前提。如果你的个性化方案已经把 LoRA 铺在多层，或者用了可训练下投影的变体，迁移就不再精确，论文只给了「保留归一化输入」的昂贵替代（保留状态 4.27 倍）。更关键的是：**作者用高斯随机适配器更新做的实验**，只隔离了迁移问题，完全没评估最后一块限制对下游任务适配质量的影响。这意味着即使复现成功，「这样训出来的适配器够不够好」仍是开放问题。

第三，**与主流服务栈脱节**。实现是进程内协调、连续序列、标准 RoPE，明确不含分页缓存（vLLM 的 PagedAttention）和分布式发布。现在没人裸写 KV 缓存管理，都是跑在推理框架上，集成路径完全空白。

第四，**盈亏平衡点要算自己的账**。论文的成本模型显示，8K 历史下对比全历史重 prefill 约需每次更新 600 token 的解码量才回本，对比边界重放则要 30 token。更新频率低、会话短的场景，收益会被 4.8% 的解码开销和额外的工程复杂度吃掉。反过来，如果你的形态是「几百个长寿会话 + 每天多次适配器滚动发布」，比如记忆型私人助理，68.98 倍的发布加速和 3.42 倍的存储节省是实打实的。

还有一个值得记下的实现教训：作者自研的最新 token 评估核误差 0.02 左右、top-1 一致率只有 96% 到 98%，换标准 SDPA 核两侧评估才做到零误差、100% 一致。做缓存迁移类系统时，别轻易手写注意力核——数值一致性验证要用同一把尺子。
