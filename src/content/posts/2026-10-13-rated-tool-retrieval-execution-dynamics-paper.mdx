## 一句话概括

arXiv 2610.13889（已接收于 CIKM 2026，10 月 9 日提交）指出了智能体工具生态里一个被普遍忽视的盲区：几乎所有工具检索方法都在优化「语义相关性」，却没人管「这个工具此刻还能不能用」。RATED 用一个轻量的上下文赌博机模块把执行时的实时反馈引入重排，在 30% API 故障率的严酷场景下，把错误选择率从 86.2% 干到 2.9%，而额外延迟不足 1 毫秒。

## 问题：静态语义匹配的三重盲区

现代智能体越来越多依赖外部工具，工具数量的膨胀让「先检索后调用」成为标配架构。但论文作者观察到，现有检索方法存在系统性缺陷：

**第一，可用性被当成常量。** 工具库描述的是理想状态，真实世界的 API 时刻在限流、改版、宕机。检索器把「语义最像」的排前面，完全不知道它排第一的那个工具五分钟前开始持续超时。

**第二，故障是长尾且时变的。** 同一个工具早上正常、下午挂掉、晚上恢复。静态索引无法表达这种时间维度，而智能体的执行失败往往不是模型推理错误，而是检索阶段就把一个已经死掉的接口推到了模型面前。

**第三，重训成本不可接受。** 把可用性信号编码进检索模型本身，意味着频繁微调。对于工具数量成千上万、状态分钟级变化的场景，这条路在工程上走不通。

## 方法：冻结双编码器 + 轻量赌博机

RATED 的架构分成两层，设计哲学是「重的冻结、轻的在线」：

**语义层**：一个冻结的双编码器（dual-encoder），经过对比学习微调，负责查询与工具描述的匹配。冻结意味着这一层不随执行状态变化，语义知识是稳定的先验。

**可靠性层**：一个轻量的上下文赌博机（contextual bandit）模块，消费实时执行反馈——哪些调用成功了、哪些超时了、哪些返回了错误码——并对候选工具重新排序。赌博机的经典优势恰好匹配这个场景：不需要昂贵的再训练，仅凭在线反馈就能快速调整策略，探索与利用的平衡天然内建。

两层解耦的好处是显式的：语义理解不动，动态适应全在轻量层完成。工具今天挂了明天恢复，赌博机几分钟内就能跟上；工具的语义描述半年不变，编码器一行权重都不用动。

## EcoAgent 基准：把「动态」变成可测的东西

论文的另一半贡献是 EcoAgent 基准——此前这个方向连一个像样的测试床都没有。规模与设计：

- **5,172 个真实世界工具**，覆盖真实 API 生态而非人造玩具接口；
- **超过 210,000 条查询-工具对**，支撑离线检索评估；
- **动态可靠性评估轨道**：可编程注入 API 故障，模拟真实世界的服务降级。

实验在两条轨道上分别验证。静态检索质量上，RATED 在真实查询上相对 ToolLLM API 检索器取得 **52.2% 的相对 MRR 提升**——注意这是在故障注入之外的正常场景，说明可靠性重排不仅没有伤害语义排序，反而因为执行信号携带了「哪个工具真的好使」的信息而获益。

动态场景的结果更醒目：在 **30% 故障率**的严重 API 中断场景下，基线方法的错误选择率高达 **86.2%**——近乎必然选中坏工具；RATED 把这个数字压到 **2.9%**。两个数量级的差距，本质是把「执行结果」这个被浪费的免费监督信号用起来了。

成本端同样关键：整个可靠性模块在仅编码推理的基础上新增延迟**不足 1 毫秒**。对于一个每轮智能体决策都要跑检索的热路径来说，这个开销意味着可以直接上生产。

## 工程意义：你的智能体栈里缺这一层

读这篇论文时值得对照自己的系统问三个问题：

**你的工具失败被记录了吗？** 大多数自建智能体把工具执行结果塞回对话就完了，没有独立的反馈存储。RATED 的前提是执行动态可观测——哪怕先用一个简单的近窗成功率计数器起步，也远好于无信号。

**你的排序考虑时间了吗？** 如果工具候选固定按向量相似度排序，那么故障期间你的智能体会稳定地、反复地撞同一堵墙。一个指数衰减的临时降权，成本一行代码。

**重训还是在线适应？** 遇到「模型总选错工具」的问题，第一反应往往是微调。这篇论文给出了反例：执行反馈驱动的轻量在线重排，可能比动模型更便宜也更及时。

## 局限与思考

论文没有展开的几个点值得留意。其一，赌博机的反馈依赖调用本身发生——一个从未被调用过的新工具缺乏执行数据，冷启动仍靠语义层兜底。其二，故障信号的定义依赖错误分类的质量：限流、超时、参数错误混在一起时，赌博机可能把「临时限流」误判为「工具劣化」。其三，5,172 个工具的规模虽大，但与企业内部动辄上万的自建工具库仍有距离，跨组织的可迁移性有待更多复现。

代码与数据集已开源在 github.com/Elliotes/EcoAgent。对做智能体基础设施的团队来说，这是近期性价比最高的一篇可复现工作：不动模型、不加延迟、只把已经在发生的执行结果接进排序层，就能把故障场景下的表现拉开两个数量级。
