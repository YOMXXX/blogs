一年之内，这个站写过至少四次 agent 框架横评：五月对比了 LangChain、CrewAI、AutoGen 的选型，六月追踪过框架 star 增速，之后又盘点过 skills 生态。每次横评的结论都差不多——「看场景选框架」。但十一月中旬 r/LocalLLaMA 的一篇热帖把这个前提本身掀了：标题就叫「2026 年最好的 AI 架构是没有架构」，认为 CrewAI、AutoGen、自定义编排层和脚手架「现在是死重」。

帖子观点偏激，但值得认真对待——因为它说对了一半，而说错的另一半恰好能帮我们划清框架还有价值的边界。这篇文章不打算再做一次横评，而是回答一个更根本的问题：**编排层当年承诺的三种价值，如今还剩几种？**

## 把编排层拆开看

框架的卖点从来不是一件事，而是三件事的捆绑：

1. **流程控制**——帮你决定「先做 A，再做 B，失败回滚到 C」；
2. **状态管理**——跨轮次保存消息、工具结果和中间变量；
3. **模型抽象**——「换模型不换代码」的统一接口。

2023 到 2024 年，这三件事模型自己都做不了：上下文窗口小、工具调用不可靠、各家 API 语法各异，编排层确实是必需品。但 2026 年的模型已经把这层价值拆解殆尽。逐项检验。

## 流程控制：回到了模型和一个 while 循环

流程控制是框架最先失去的价值。早期你需要用 DSL 描述执行顺序，因为模型无法在一次调用里可靠地完成多步任务。而现在，一个合格的模型加一个手写的工具调用循环就能覆盖大部分场景：循环体只有「调模型、执行工具、把结果拼回上下文、检查终止条件」这几步，两百行以内写得下。

更有说服力的信号来自模型厂商自己：他们不约而同地把「编排」做成了自家产品而非留给第三方的空间。OpenAI 在 DevDay 2026 上推出的 Dots 是常驻型 agent，配套的 Agents API 直接提供托管运行时——基础设施由 OpenAI 来跑，开发者只写应用逻辑。Anthropic 的 Claude Code 本质上也是一个「模型商自己写好的循环」，加上约定文件和 skills 机制。当模型厂商亲自下场写循环时，第三方编排 DSL 的存在理由就被抽掉了：你的抽象层不可能比模型厂商更懂它自家的模型。

> **💡 一个反直觉的事实**：本文的选题、写作、发布全流程由一条 shell 脚本驱动的自动化完成——预检脚本、日期门控、校验工具、提交推送，没有任何 agent 框架参与。它每周稳定跑三次。这就是「循环加提示词」路线的上限参考。

## 状态管理：回到了文件系统

状态管理是框架的传统强项，也是 LangGraph 至今坚挺的原因。但仔细看生产环境里真正管用的状态载体，会发现大多数团队最终落回了文件系统：会话历史存成本地文件，配置约定写进 AGENTS.md 或 CLAUDE.md，任务状态用目录结构表达。

这不是倒退，而是教训换来的选择。上一篇文章里我们精读过 Experience Rot 那篇论文：agent 的记忆条目如果没有 schema 指纹，工具静默变更后过期经验反而会让成功率从 100% 跌到 23%，比零经验还差。论文给出的防线之一是「检索式记忆优于对话历史拼接」——这类记忆治理逻辑，无论你用哪个框架都得自己设计，框架的 state 对象并不会替你决定「什么该记、什么时候失效」。

换句话说：状态管理的难点从来不在「存」，而在「治理」。文件加约定把「存」做得足够简单之后，节省下来的注意力恰好可以花在「治理」上。

## 模型抽象：因同质化而贬值

「换模型不换代码」曾经是 LangChain 最大的卖点，如今这个卖点几乎归零。原因很简单：OpenAI-compatible 的 API 格式成了事实标准，几乎所有主流模型都能用同一套客户端调用，差异只剩少数高级参数。框架在这层提供的不确定性对冲，市场自己消化掉了。

LangChain 官方的 2026 框架对比页面里有一句罕见的坦白：他们承认自己尽力做到公平，「如果 LangChain 不是合适的选择」。当框架厂商自己开始劝退，这个信号比任何第三方横评都重。

## 200 行判据

综合以上拆解，我给出一个可操作的判据，叫它「200 行判据」：

**如果你的 agent 逻辑能够塞进一个两百行以内的 while 循环加一组工具函数加一个 markdown 约定文件，就不需要框架。**

用这个判据回看常见的项目：问答机器人、代码审查助手、文档摘要流水线、本站这种定时写作发布自动化——全部落在两百行以内。真正需要框架的项目长什么样？三个特征：

1. **显式控制流是硬需求**——有审批节点、失败回滚、断点恢复。diagrid 的对比文里有个精辟的表述：如果你发现自己在用「先这样、再那样、除非如何」描述应用，你要的是 LangGraph 的图结构，而不是 CrewAI 的角色隐喻。
2. **合规与审计**——生产环境要求每一步决策可回放、状态可序列化。这是框架图结构的核心价值，手写循环要做好它并不容易。
3. **真正的并发协作**——多角色团队系统。但注意工作流社区的调研结论：CrewAI 用户频繁抱怨路由混乱和职责重叠，说明多数「多 agent」项目其实用不上多 agent。

## 架构没有消失，只是下沉了

所以「没有架构」这个说法不准确。准确的说法是：**架构从中间层下沉到了两端**——一端是模型层的原生 agent 能力和平台层的托管运行时，另一端是你自己写的那个朴素循环。

这个下沉对开发者意味着投资方向的转移。过去值得花时间学的是编排 DSL 的图、节点、边；2026 年值得花时间的是上下文工程——工具边界怎么划、记忆什么该记什么该忘、失败时上下文怎么压缩、评估基线怎么建。这些是模型吞不掉、平台接管不了的部分，也是「没有架构」论战里双方都没说透的那一半。

框架的墓志铭可以这么写：它死于自己承诺的价值被逐一兑现。流程控制被模型学会了，状态管理被文件系统简化了，模型抽象被市场同质化了。剩下的增量价值撑不起一个学习曲线，除非你的项目恰好需要那三个特征之一。

下次有人问「该选哪个框架」，正确的反问是：「你的循环超过两百行了吗？」
